## 二、第一轮：自查修复

### 1.（高）重试链路未使用改写后的查询

- **位置**：`graph/nodes.py`、`graph/edges.py`
- **现象**：触发重试时第二轮检索重复原始查询，而生成阶段按改写后的查询作答 —— 检索与生成口径不一致，重试形同虚设。
- **根因**：`rewrite_query_node` 把改写结果写进 `state["current_query"]`，但 `knowledge_search` 取查询用的是 `_latest_user_text(state)`（最后一条 `HumanMessage`），从不读 `current_query`。
- **修复**：新增 `nodes._active_query(state)` 作为唯一取值口径，`knowledge_search` 与 `generate_node` 共用。（该函数第二轮被修正，见 12。）
- **验证**：桩件（假 retriever 记录查询 + 假 LLM 返回"未找到"触发重试）跑通完整图：`retriever calls: ['原始查询', '改写后的查询X']` → **PASS**。断言非空洞：第二个值不等于最后一条用户消息。

### 2.（高）`--offline` 会污染真实向量库

- **位置**：`test_agent.py`
- **现象**：空库场景下按 README 建议跑 `--offline` 冒烟，会把 19 个 **8 维** dummy 向量写进真实 `personal_knowledge` 集合；之后再跑 `main.py`，因集合非空跳过建索引，但查询用 **512 维**向量，维度不符导致检索报错且无法自愈（只能 `--rebuild`）。
- **根因**：只替换了 embedder，沿用了同一 `chroma_db_dir` 与集合名。
- **修复**：新增 `_offline_settings()`，指向临时目录 + 独立集合名。（该修法第二轮被补强，见 16/17。）
- **验证**：运行前后 `data/chroma` 集合列表不变；真实集合仍 `count 19 / dim 512` → **PASS**。
- **诚实说明**：**没有故意复现**"污染后查询失败"的破坏性场景（会毁掉当前索引）。该缺陷是代码路径推演结论：同一 `PersistentClient` + 同一集合名，Chroma 集合维度在首次写入时固定。

### 3./4.（中）`-q` 与 `test_agent.py` 复用固定 `thread_id`

- **证据**：`data/checkpoints.sqlite` 中 `one-shot` 线程已累积 36 条记录、`test` 线程 24 条 —— 固定 id 复用同一份持久化历史，导致"单次提问"带上上次运行的上下文。
- **修复**：改为每次运行一次性 `one-shot-<uuid8>` / `test-<uuid8>`。（第二轮发现该修法会造成线程泄漏，见 13。）

### 5.（中）`create_note` 同标题重复保存导致索引重复

- **现象**：同标题再保存，文件被覆盖但旧片段仍留在向量库（新片段用新 UUID 追加），检索会同时命中新旧两份。
- **修复**：改为按来源清理旧片段。（第二轮发现修法有两个严重问题，见 9/10。）

### 6.（低）`create_note` 忽略配置的分块参数
`split_documents([doc])` 用函数默认值，而建索引用 `settings.chunk_size/chunk_overlap`。已改为由 `get_tools` 注入。

### 7.（低）空 AI 消息被当作对话历史发送
`knowledge_search` 追加的 `content=""` + `tool_calls` 的 `AIMessage` 会被 `_to_dict` 剥掉 tool_calls，成为一条空 assistant 轮次送给模型，并被 checkpoint 永久保留。已在 `_trim_history` 中过滤（该过滤器第二轮被修正，见 18）。

### 8.（低）`generate_node` 死代码分支会注入错误查询
原 `if query.startswith("INTENT:"): query = query.split(":", 1)[1]` 一旦执行，`query` 会变成字面量 `"knowledge"`。已删除，改用 `_active_query`。

### 9.（高，我引入）按文件名删除会误删同名 KB 文档

## 四、第三轮：实现工具调用循环（应你的决定）

**你选择了「实现工具调用循环」**，因此原来列在「未修复」里的第一项已落地。这里记录设计与验证边界。

### 原问题（原有，我第一轮漏掉）

`grep bind_tools` 只命中注释；`ZhipuLLM._invoke` 不传 `tools=`/`tool_choice`，`_to_dict` 还丢弃 `tool_calls` —— 模型既看不到工具定义也无法返回工具调用，图中只有 `knowledge_search` 是通的。后果：与规格「原生 Function Calling」不符；提示词要求模型"记录新内容时调用 `create_note`"却做不到，**有诱导模型谎称"已保存"的风险**；我第一轮对 `create_note` 的两处修复都落在跑不到的路径上。

### 实现

1. **适配器侧（`graph/llm.py`）**
   - `ainvoke(messages, tools=None)` 新增 `tools` 参数；`_tools_to_payload()` 把 langchain `BaseTool`（取 `tool_call_schema`，回退 `args_schema`，再回退空 object schema）序列化为 OpenAI function-calling 载荷，并带 `tool_choice="auto"`。
   - `_normalize_tool_calls()` 把 SDK 返回的 `tool_calls` 归一成 `{"id","name","args","parse_error"}`。**参数 JSON 解析失败时 `args=None` + `parse_error`**，而不是静默变成 `{}` —— 否则 `create_note` 会以空参数被调用，等于"保存一条空笔记"。
   - `_to_dict()` 现在会把 assistant 轮次的 `tool_calls` 原样发回（否则后续的 tool 结果无所依附）。
   - 流式与工具互斥：带 `tools` 的调用强制走非流式（流式 delta 不携带 tool calls，会丢）。
   - **不传 `tools` 时行为与改动前逐字节一致。**
2. **节点侧（`graph/nodes.py`）**
   - 新增 `_tool_enabled_completion()`：把 `DEPS.tools` 交给模型 → 若返回 `tool_calls` 则逐个执行 → 把 `AIMessage`(带 tool_calls)+`ToolMessage` 追加进对话后再次调用 → 直到模型给出纯文本答案；轮次上限 `settings.max_tool_iterations`（新增配置，默认 3），耗尽时返回明确文案而非静默收尾。
   - `_execute_tool_call()`：未知工具、参数不是对象、参数 JSON 畸形、工具内部抛错 —— 全部以**文本**回给模型由它决定下一步（规格要求 "structured error → LLM decides"），不让整轮崩掉。
   - `_llm_accepts_tools()` 用 `inspect.signature` 判断 LLM 是否支持 `tools=`（而非捕获 TypeError，避免把调用内部的 TypeError 误判成"不支持工具"），因此桩件/自定义 LLM 也能工作。
   - `generate_node` **与** `direct_response` 都改走这条路径 —— 后者同样必要：`_classify_intent` 会把"帮我记一下"判成 chat 分支，只改知识分支的话这个功能对它的主要用例仍然不可达。
   - 若 API 拒绝我们的 tools 载荷，**自动降级**为不带工具的一次调用并打 warning，保证可用性不因这次改动而回退。

`rag/reranker.py` 给 query 加了 `"为这个句子生成表示以用于检索相关文章："`。该前缀属于 bge **向量**模型用法，`bge-reranker-v2-m3` 作为 CrossEncoder 官方用法不需要它，加了可能**降低**重排精度。未改原因：本地 `RERANKER_ENABLED=false`，验证需下载约 2GB 模型做 A/B，我无法给出量化结论。
