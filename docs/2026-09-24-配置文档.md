## 1. 配置的生效规则（先看这节，能挡掉大部分"改了不生效"）

| 规则 | 说明 |
|---|---|
| **配置来源只有一个** | `config.Settings`。`rag`、`tools`、`graph` 全部从它读取，没有第二处配置文件。 |
| **优先级：真实环境变量 > `.env` 文件 > 代码默认值** | 已实测：`.env` 里是 `EMBEDDING_BACKEND=local`，用 `EMBEDDING_BACKEND=zhipu .venv/bin/python ...` 启动时读到的是 `zhipu`。临时改配置不必动文件。 |
| **改完 `.env` 必须重启进程** | `get_settings()` 带 `@lru_cache(maxsize=1)`，一个进程内只实例化一次。 |
| **拼错变量名不会报错** | `SettingsConfigDict(extra="ignore")`，已实测：设了 `KB_DIRX=/tmp/nope` 不抛异常、也不生效，静默使用默认值。写错名字时表现为"配置没反应"，而不是报错。 |
| **`.env` 里的路径是相对路径** | `.env` 写的是 `KB_DIR=./data/kb`，pydantic 会加载成**相对路径** `data/kb`（已实测 `is_absolute() == False`），最终位置由**进程 cwd** 决定。<br>👉 因此**必须在 `personal-knowledge-agent/` 目录下运行**，否则知识库、向量库、checkpoint 会落到别处（甚至凭空新建空库）。 |
| **`HF_ENDPOINT` 会被代码自动补默认值** | `config.py` 在 import 时若发现该变量为空，会设为 `https://hf-mirror.com`（国内下载本地模型用）。自己设了就以自己设的为准。 |
| **`.env` 不在 git 里** | 已被 `.gitignore` 忽略；`.env.example` 才是入库的模板。 |

## 3. 配置项之间的约束与相互作用

1. **切 `EMBEDDING_BACKEND` 必须跟一次 `--rebuild`**
   两种后端产出的向量维度不同（`local` 的 `bge-small-zh-v1.5` 为 512 维，已实测）。已有向量与新查询向量维度不符会导致检索失败，且因"集合非空就跳过建索引"的逻辑不会自愈。命令：`python main.py --rebuild`。

2. **关掉重排器时 `RERANK_TOP_K` 仍然生效**
   不重排时由 `Retriever._raw_top` 按原始相似度截断到 `rerank_top_k` 条，所以关掉重排不等于"多给上下文"。

3. **索引是全量模型，配置改动不自动重建**
   启动时仅当集合为空才建索引；删改 `data/kb/` 里的文档不会被清理。改 `CHUNK_SIZE`/`CHUNK_OVERLAP` 或换 embedding 后端后，都必须 `--rebuild` 才生效。

4. **`create_note` 与建索引共用同一套分块参数**
   自 2026-09-24 修复起，`create_note` 从 `settings.chunk_size/chunk_overlap` 取值（此前硬编码 512/64）。同标题重存会替换该笔记的旧片段（`VectorStore.reindex_path()`，按文件的 `path` 定位、先加后删），因此不会产生重复片段，也不会因中途失败而丢失旧内容。

5. **`RERANK_TOP_K ≤ TOP_K`**
   没有代码强制校验。若配反了，实际返回条数是 `min(候选数, rerank_top_k)`，表现为"召回变少"。

6. **`MAX_RETRY` 与答案质量的判定口径**
   触发重试的条件是「本次检索为空」**或**「答案里出现 `未找到`/`没有找到`/`not found`/`未收录`」。所以要避免把 `MAX_RETRY` 调大来"提升质量"——重试只会用改写后的查询再检索一次，不会换答案风格。

7. **`MAX_HISTORY_MESSAGES` 与 checkpoint 的关系**
   调小它只是少喂上下文，`data/checkpoints.sqlite` 里的历史仍然持续累积（该库不自动清理）。

8. **工具调用轮次与模型选择相互影响**
   三个工具都以原生 Function Calling 交给模型，由生成节点执行并把结果回灌，往返次数由 `MAX_TOOL_ITERATIONS` 封顶。调大它可以让模型做更长的多步操作，但也成倍增加 token 消耗；调成 `1` 等价于"最多调一次工具就必须作答"。工具执行失败不会中断流程，而是以文本回给模型（由它决定重试或放弃）。

9. **单次运行可用环境变量覆盖，无需改文件**
   ```bash
   EMBEDDING_BACKEND=zhipu python main.py -q "问题"
   CHROMA_COLLECTION_NAME=exp1 python main.py          # 另起一套隔离知识库
   ```

## 4. 常见配置场景

### 场景 A：全新搭建（最小可用）
```bash
cd personal-knowledge-agent
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env      # 只改一行：填 ZHIPU_API_KEY
python test_agent.py --offline   # 先验流水线，不耗额度、写临时库
python main.py                   # 正式跑（会把 data/kb 建索引）
```

### 场景 B：不想下载本地 embedding 模型
把 `EMBEDDING_BACKEND` 设为 `zhipu`。**前提**是智谱账户有 embedding 资源包（与聊天资源包分开），否则调用会失败。切换后务必 `--rebuild`。

### 场景 C：省流量/不想装重排器
保持 `RERANKER_ENABLED=false`（当前 `.env` 即此值）。检索仍可用，只是用原始向量分数排序；开启但模型加载失败时也会自动降级，只打印一条告警。

### 场景 D：多套知识库互不干扰
同时换掉这两个变量即可：
```bash
CHROMA_DB_DIR=./data/chroma_exp CHROMA_COLLECTION_NAME=exp1 KB_DIR=./data/kb_exp python main.py
```

### 场景 E：只想验证代码没坏，不花一分钱
```bash
python test_agent.py --offline
```
它用 8 维确定性假向量，且**写入临时目录**（自 2026-09-24 修复起），不会碰你的真实向量库。

## 5. 代码内固定参数（改不了配置，只能改代码）

| 参数 | 位置 | 值 |
|---|---|---|
| 生成温度 | `graph/builder.py` | `temperature=0.3` |
| 生成 `max_tokens` | `graph/llm.py` `DEFAULT_MAX_TOKENS` | `8192`（留足思考过程 + 最终答案的预算，**调小会导致空回答**） |
| 意图分类调用 | `graph/nodes.py` `_make_classifier_llm` | `temperature=0`、`max_tokens=16`、`thinking={"type":"disabled"}` |
| 分块分隔符优先级 | `rag/splitter.py` | `["\n\n", "\n", "。", "；", " ", ""]` |
| 重排器 query 前缀 | `rag/reranker.py` `_PREFIX` | `为这个句子生成表示以用于检索相关文章：`（**疑似误用**，见修复报告第三节第 1 条） |
| 支持的文件类型 | `rag/loader.py` | `.md` / `.markdown` / `.txt`，非递归，跳过 `.`/`_` 开头的隐藏文件 |
| 笔记文件名规则 | `tools/create_note.py` | 标题中 `\/:*?"<>|` 替换为 `_`，空白折成 `_`，截断 80 字符，保留中文 |
| 系统提示词 | `prompts/system_prompt.py` | 按规格**禁止**写入 CoT/ReAct 指令（GLM-5.2 自带思考） |

## 7. 故障排查速查表

| 症状 | 大概率原因 | 处理 |
|---|---|---|
| 改了 `.env` 完全没反应 | 变量名拼错（`extra="ignore"` 静默忽略），或进程没重启 | 对照第 2 节表核对变量名；重启进程 |
| 回答是空的 | `max_tokens` 被改小，思考过程吃光预算 | 恢复 `graph/llm.py` 的 `DEFAULT_MAX_TOKENS=8192` |
| `Numpy is not available` | 装到了 numpy ≥ 2（与 torch 2.2.x ABI 不兼容） | `pip install 'numpy<2'` |
| 检索报维度相关错误 | 换过 `EMBEDDING_BACKEND` 但没重建索引 | `python main.py --rebuild` |
| 启动即退出，提示 API Key | `ZHIPU_API_KEY` 为空 | 填 `.env`，或先用 `test_agent.py --offline` |
| 找不到知识库/知识库是空的 | 没在 `personal-knowledge-agent/` 下运行，相对路径指到了别处 | 切到代码目录再跑 |
| 日志出现重排器告警但仍能回答 | 模型加载失败后的**预期降级** | 无需处理；要彻底关掉设 `RERANKER_ENABLED=false` |
| `Reranker disabled via RERANKER_ENABLED=false` 报错 | 开启与关闭状态不一致（如代码里显式调用重排器） | 属预期，非故障 |
| 答案受上次提问影响 | 复用同一 `thread_id` | `-q`/`test_agent.py` 已改为一次性 thread 且跑完即删（2026-09-24 修复）；自定义调用请自行保证 thread 唯一并负责清理 |
| 回答变成"（已达到工具调用次数上限…）" | 模型连续请求工具超过 `MAX_TOOL_ITERATIONS` | 调大该值；若反复发生，检查工具是否一直报错（日志里有 `Tool … failed`） |
| 日志出现 `Tool-enabled call failed; retrying without tools` | API 拒绝了 tools 载荷 | 退化为无工具调用，回答仍会产出；需检查 `_tools_to_payload` 产出的 schema |
